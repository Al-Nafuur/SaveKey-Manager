Klar. Ich würde den aktuellen Stand für TinyELF BASIC + SaveKey/EEPROM-Disk so festhalten. Einige Details sind bewusst noch als „zu definieren“ markiert.

1. Grundidee

Wir behandeln den EEPROM-SaveKey nicht mehr nur als klassischen SaveKey für ein einzelnes BASIC-Programm, sondern als kleines Block-/Diskmedium.

Die BASIC-Ebene soll später ungefähr:

SAVE "E1:TEST.BAS"
LOAD "E1:TEST.BAS"
CATALOG "E1:"

ermöglichen.

Das Dateisystem orientiert sich stark an Atari DOS 2.x, soll aber für kleine EEPROMs effizienter und für größere EEPROMs erweiterbar sein.

2. Sektorgröße wird an EEPROM-Page-Size angepasst

Das ist eine der wichtigsten Entscheidungen.

Statt immer 128 Byte zu verwenden, soll die logische Sektorgröße zur Page-Größe des EEPROMs passen:

EEPROM	Kapazität	Page	vorgeschlagene Sektorgröße
24LC32	4 KiB	32 B	64 B
24LC64	8 KiB	32 B	64 B
24LC128	16 KiB	64 B	64/128 B
24LC256	32 KiB	64 B	64/128 B
24LC512	64 KiB	128 B	128 B
24LC1024/1025	128 KiB	128 B	128 B
AT24CM02	256 KiB	256 B	256 B

Der genaue Grenzpunkt zwischen 64 und 128 Byte ist noch festzulegen.

Der große Vorteil:

Ein kompletter Filesystem-Sektor kann idealerweise mit einem EEPROM-Page-Write geschrieben werden.

3. Sektoradressierung

Wir wollen uns an der Atari-DOS-2.x-Logik orientieren.

Die klassische DOS-2.x-Sektorverkettung verwendet eine 10-Bit-Sektornummer. Damit sind maximal:

1024 Sektoren

adressierbar.

Das ergibt je nach Sektorgröße:

1024 × 64  =  64 KiB
1024 × 128 = 128 KiB
1024 × 256 = 256 KiB

Damit passt der AT24CM02 mit 256 KiB sehr schön in dieses Schema.

Für 512 KiB müssten wir die Sektoradressierung erweitern, z.B. auf 16 Bit.

4. Nicht immer 1024 Sektoren!

Das haben wir zuletzt korrigiert:

1024 ist die maximale Anzahl, nicht die feste Anzahl.

Beispielsweise:

4 KiB   / 64 B  = 64 Sektoren
8 KiB   / 64 B  = 128 Sektoren
32 KiB  / 64 B  = 512 Sektoren
128 KiB / 128 B = 1024 Sektoren
256 KiB / 256 B = 1024 Sektoren

Die tatsächliche Anzahl der Sektoren steht im Header bzw. ergibt sich aus dem Medium.

5. DOS-2.x-Sektor-Control-Information

Wir möchten das Prinzip der Atari-DOS-2.x-Datensektoren beibehalten:

3 Bytes pro Sektor für:

nächsten Sektor
Dateinummer
Anzahl gültiger Datenbytes

Bei 128-Byte-Sektoren bleiben damit:

128 - 3 = 125 Byte Nutzdaten

Bei größeren Sektoren müssen wir noch entscheiden, ob die Control-Struktur immer 3 Byte bleibt oder ob sie für 256-Byte-Sektoren erweitert wird.

Ich würde zunächst versuchen, 3 Byte beizubehalten, um möglichst nahe an DOS 2.x zu bleiben.

6. Directory

Wir übernehmen das Atari-DOS-Prinzip:

16 Byte pro Directory Entry

→ bei einem 128-Byte-Sektor:

8 Einträge / Sektor

Für kleine EEPROMs soll das Directory nicht wie beim klassischen DOS 2.x pauschal 8 Sektoren groß sein.

Unsere bisherige Idee:

4 KiB   → 1 Directory-Sektor → 8 Dateien
8 KiB   → 1 Directory-Sektor → 8 Dateien
16 KiB  → 2 ...
32 KiB  → 4 ...
64 KiB+ → ggf. 8 → 64 Dateien

Die genaue automatische Staffelung ist noch offen.

Für einen 4-KiB-Entwickler-SaveKey sind 8 Dateien wahrscheinlich völlig ausreichend.

7. VTOC

Auch hier übernehmen wir das Atari-Prinzip einer Allocation Bitmap:

1 Bit = 1 Sektor

Dadurch ist die VTOC für kleine Medien sehr klein:

64 Sektoren   → 8 Byte Bitmap
128           → 16 Byte
256           → 32 Byte
512           → 64 Byte
1024          → 128 Byte

Wir wollen die VTOC aber nicht zwingend auf Sektor 360 legen.

Das ist wichtig für 4/8/32 KiB.

8. Flexibles Disk-Layout

Das ist wahrscheinlich die wichtigste Abweichung vom historischen DOS 2.x.

Im originalen DOS 2.x liegen VTOC und Directory an festen Stellen, insbesondere:

VTOC       Sektor 360
Directory  361–368

Das ist für kleine EEPROMs völlig ungeeignet.

Unser Header soll deshalb beispielsweise enthalten:

Total sectors
Sector size
VTOC start
VTOC size
Directory start
Directory size
Filesystem version

Damit kann FORMAT das Layout abhängig von der EEPROM-Größe erzeugen.

9. Boot/Header

Wir wollen uns am 384-Byte-DOS-2.x-Bootbereich orientieren, ihn aber nicht unnötig groß machen.

Der erste Sektor soll einen TinyELF-DOS-Header enthalten.

Darin sollen insbesondere die variablen Parameter des Mediums stehen.

Sinngemäß:

TinyELF Disk Header

Filesystem version
Sector size
Total sectors
VTOC start
VTOC size
Directory start
Directory size
Flags
...

Außerdem soll BLDISP bzw. dessen Funktion berücksichtigt werden, weil die historische DOS-2.x-Logik zwischen 128- und 256-Byte-Sektoren unterscheidet.

Für unser eigenes Format würden wir das vermutlich etwas allgemeiner als Sector Size Code definieren:

64
128
256
10. Kleine EEPROMs sind ein Sonderfall

Für 4–32 KiB wollen wir kein vollständiges historisches DOS-2.x-Layout erzwingen.

Beispielsweise würde ein klassisches 4-KiB-DOS-2.x-Layout absurd viel Platz verschwenden:

3 × Boot       = 384 B
VTOC           = 128 B
Directory      = 1024 B
                     ─────
                     1536 B

→ 37,5 % des gesamten 4-KiB-EEPROMs wären bereits Verwaltung.

Deshalb:

DOS-2.x-kompatible Datenstrukturen, aber kompaktes und variables Layout.

11. FORMAT

FORMAT soll die Größe entweder aus dem EEPROM erkennen oder optional einen Typ vorgegeben bekommen.

Die Idee war z.B.:

TYPE 1 = 32 KiB
TYPE 2 = 64 KiB
...

Noch besser wäre aber eine automatische Erkennung über die tatsächlich vorhandenen I²C-Devices/Adressen plus die beim Formatieren gewünschte Größe.

Wichtig dabei:

Wir müssen nicht unbedingt wissen, ob hinter mehreren aufeinanderfolgenden I²C-Adressen mehrere EEPROMs oder ein großer EEPROM steckt.

Für das Filesystem ist nur relevant:

logischer Speicher = X KiB
12. I²C und Filesystem werden getrennt

Architektonisch würde ich es ungefähr so aufbauen:

TinyELF BASIC
      │
      ▼
 File System
      │
      ▼
 Block Device API
      │
      ├── I²C EEPROM
      │
      └── später SIO

Das ist wichtig für die Zukunft.

Wenn wir später SIO-Disketten unterstützen, muss das Filesystem nicht komplett neu geschrieben werden.

13. Ziel für SIO

Für D1: usw. wollen wir später möglichst echte Atari-Diskstrukturen unterstützen.

Dabei ist DOS 2.x/MyDOS die Referenz.

Die I²C-EEPROM-Disk (E1:) muss aber nicht physisch exakt dasselbe Layout verwenden, solange die Dateisystemlogik kompatibel bzw. konvertierbar bleibt.

So könnten wir später haben:

E1:  → I²C EEPROM
E2:  → I²C EEPROM
D1:  → SIO Disk
D2:  → SIO Disk

und darüber dieselben BASIC-Befehle.

Die derzeitige Kernentscheidung in einem Satz

Ein kleines, variables TinyELF-Diskformat, das sich an Atari DOS 2.x orientiert (Directory, VTOC, Sektorverkettung), dessen Layout und Sektorgröße aber an die tatsächliche EEPROM-Kapazität und Page-Size angepasst werden.

Damit können wir 4-KiB-EEPROMs als günstige Software-/Demo-Medien genauso unterstützen wie den 256-KiB-AT24CM02 als vollwertige „Diskette“, ohne für jede Größe ein komplett anderes Filesystem zu benötigen.
